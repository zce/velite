## Question

Which benchmark workloads, metrics, regression limits, and structural assertions must the selected 1.0 design satisfy before implementation is accepted?

## Answer

### Benchmark workload matrix

All generated documentation documents are deterministic and 1.5-2.5 KiB unless a row says otherwise. A normal document has frontmatter, three to five headings, prose, a list, and, for MDX, static JSX plus one expression/ESM declaration. Timed full builds use the built `dist/index.mjs` entry and real filesystem, config loading, validation, content processing, assets, and single-layout output. Deterministic structural tests may instead use internal factories, test adapters, and controlled plugin counters; they must not add a public broker/cache inspection interface.

The checked-in benchmark implementation may factor these rows into fewer fixture generators, but it must preserve each row's independently reportable result. In particular, its 144.4 ms frontmatter, 283.2/342.6 ms Markdown, 862.4/963.6 ms MDX, 3,364.6 ms mixed full build, 63.4 ms no-op, 15.1 ms incremental, and 373.4 MB RSS values must not be compared directly across machines or changed toolchains.

### Measurement protocol

1. Record the baseline and candidate commit, exact Node executable/version, OS/kernel, architecture, CPU model and logical-core count, total memory, pnpm version, and lockfile hash with every result. Baseline and candidate must use the same Node executable, host, power/performance mode, dependency lockfile, environment variables, and benchmark harness. Dependency changes must either be excluded or measured as a separate explicitly attributed comparison.
2. Run `pnpm build` for each revision and benchmark its built `dist/`; do not benchmark TypeScript source through jiti as the product path. Fixture generation, output cleanup, and result serialization are outside the timed region. A cold full-build sample starts a fresh Node process with no builder, broker, output generation, or application module state and ends after required output is written. Importing `dist/index.mjs`, loading config, and creating the builder are inside the cold end-to-end interval.
3. "Cold" does not claim an empty kernel page cache. Do not require privileged OS cache dropping. Use two unmeasured fresh-process warm-up pairs to populate/stabilize filesystem caches, then seven measured independent-process baseline/candidate pairs. Alternate pair order AB/BA and randomize workload order from a recorded seed so thermal or background drift does not systematically favor one revision.
4. The no-op and single-file measurements run after the full build in the same builder process because warm incremental state is the subject under test. Each of their seven measured samples still starts from a separate fresh full-build worker. The changed document and event are identical for baseline and candidate.
5. Gate ratios use the median of the seven paired `candidate / baseline` ratios. Also report each revision's median, min/max, median absolute deviation, arithmetic coefficient of variation, and nearest-rank p95 as an advisory tail indicator. Never pass from the fastest sample. Wall-time batches are valid only when each side's coefficient of variation is at most 5%; no-op and single-file batches may use 8%. Peak-RSS batches must have coefficient of variation at most 5%.
6. Sample worker RSS every 2 ms on the dedicated Linux release host using `/proc/<pid>/status` (or a validated equivalent with no lower sampling fidelity). Report the median and maximum sampled peak RSS across workers; gate the median paired ratio and retain the maximum as advisory evidence. End-of-operation `process.memoryUsage()` is supplemental and is not a peak-RSS substitute.
7. Boundary/noise classification uses Ticket 25's gate-specific dimensionless ratio margin, reduction margin, or normalized allowed-delta margin. A qualifying boundary, a baseline/candidate ordering that changes across halves of the batch, or a protocol-listed stability invalidity may authorize one complete same-protocol rerun. Both batches remain in the report. For a valid boundary rerun, the second batch and the pooled 14-pair median must pass. For an invalid first batch, the second valid batch is authoritative. A second invalid or failing batch does not pass and cannot be replaced by selecting samples.
8. The 20,000-document series uses the same two warm-up and seven measured-pair policy on the dedicated host. Time growth is evaluated from median full-build times. RSS growth uses peak RSS above an idle-worker baseline measured in the same batch. Fixture byte sizes and document/asset counts are verified before timing.

### Structural correctness/performance assertions

Every assertion below is a hard gate. A wall-time or memory improvement cannot compensate for any violation.

- Matching selected text, source path, dialect, and effective parse profile for a root, TOC, and excerpt invoke one pristine parse per record/profile. Concurrent matching siblings await the same pending parse.
- Equivalent independently-created roots share according to normalized effective profile; root object identity is never a key. Different text, source path/origin context, dialect, or effective parse profile never shares. Opaque/cyclic values obey the conservative same-reference rules already selected.
- A projection-only Markdown or MDX demand performs the dialect-correct pristine parse and only the demanded static projection. It performs no primary render, transform, MDX compile, recma phase, or minification.
- Every demanded transforming branch runs its requested transform/compiler/minifier phases exactly once and receives observably isolated AST/VFile state. Parse, transform, compile, minify, projection, and branch-materialization counters are all reported. The implementation may choose clone, ownership transfer, copy-on-write, persistent data, or another safe mechanism, but it may not hide an extra parse/retry or share mutable branch state.
- A matching rejected parse is attempted once, retained for every matching waiter until record disposal, and never retried. Unrelated identities continue independently.
- Broker disposal is idempotent and terminal. After every successful, invalid, throwing, rejected, abandoned, or late-settling record validation, retained broker slot, AST, VFile seed, branch AST/VFile, promise, outcome, diagnostic, effect, and projection-result counts are zero. Another record or rebuild never observes the disposed artifact.
- There is no cross-record or cross-rebuild artifact sharing. Unchanged records may be skipped by the Engine, but every actually revalidated record opens a new broker.
- Asynchronous sibling or asset completion order does not change primary values, static MDX semantics, TOC/excerpt values, byte output, diagnostics, messages, effects, URLs, or their canonical ordering and provenance.
- Invalid records commit no effects, including effects from successful siblings. Unique conflicts invalidate every participant. Shared parse failures retain one root cause while preserving one field-associated diagnostic per demand.
- Asset adapter counters distinguish reference occurrences, unique computation identities, and output destinations. A fixture expecting one unique computation must perform no duplicate expensive read/hash/probe/blur; initial publication writes each unique destination once; no-op publication writes none; partial failures publish no candidate manifest or data.
- Failed full or incremental builds, missing assets, output failures, `prepare` rejection, and strict-upgraded errors publish no new generation and delete no previously committed output. `prepare(false)` still obeys fatal/strict gates and reconciles output only on a successful commit.
- Candidate output is equivalent to the isolated semantic oracle for Markdown/MDX primary values, static MDX handling, TOC/excerpt whitespace and truncation, diagnostics count/path/code/severity/order, effect identity/order, linked assets/public URLs, `prepare(false)`, fatal gates, and incremental committed generation.

Instrumentation belongs at existing internal seams: injected parser/dialect adapters, controlled Unified plugins, schema closures, counting filesystem/image adapters, writer results, and record-lifetime weak-reference/retention probes where reliable. It must not expose a broker, cache key, slot registry, statistics object, or debug lifecycle operation through the public interface.

### Numeric regression gates and improvement targets

All percentages compare adjacent baseline and candidate runs under the protocol above. Historical absolute milliseconds are advisory context only.

| Metric                                                    |                        Hard regression gate |                       Target improvement | Advisory observation                             |
| --------------------------------------------------------- | ------------------------------------------: | ---------------------------------------: | ------------------------------------------------ |
| 100-document Markdown primary-only median                 |            Candidate no more than 5% slower |                            No regression | p95, CPU/heap, branch-materialization cost       |
| 100-document MDX primary-only median                      |            Candidate no more than 5% slower |                            No regression | Compile versus minify split                      |
| 100-document Markdown combined total median               |            Candidate no more than 3% slower |                             Faster total | Projection-only time and allocation              |
| 100-document MDX combined total median                    |            Candidate no more than 3% slower |                             Faster total | Compile/minify dominance                         |
| Combined TOC/excerpt overhead, separately per dialect     |                          At least 30% lower |                       At least 50% lower | Absolute paired delta in milliseconds            |
| 1,000-document mixed full build                           |            Candidate no more than 5% slower | At least 3% faster in both valid batches | p95 and phase attribution                        |
| 1,000-document no-op rebuild                              | Regression no greater than `max(10%, 2 ms)` |                            No regression | Engine revision and scan/read counts             |
| 1,000-document single-file rebuild                        | Regression no greater than `max(10%, 2 ms)` |                            No regression | Number of revalidated sources/records and writes |
| Peak RSS for 100 combined, 1,000 mixed, and 20,000 stress |           Candidate no more than 10% higher |               Lower retained/peak memory | Maximum sampled peak and end heap                |
| 20,000-document full-build time                           |           Candidate no more than 10% slower |                            No regression | Throughput per document                          |

For dialect `d`, combined overhead reduction is:

```text
1 - ((candidate_combined_d - candidate_primary_d) /
     (baseline_combined_d - baseline_primary_d))
```

The primary and combined values in this calculation must come from the same randomized batch. A non-positive baseline denominator invalidates that workload batch rather than manufacturing a pass. The 30% floor is a hard acceptance gate; 50% is the intended improvement. This is more defensible than making 50% hard because the old overhead includes both the removable second parse and still-required projection traversal, while the new design also pays for branch isolation, profile normalization, and transactional outcomes.

Stress growth is a hard affine-growth check, not a fixed millisecond budget. Let the early marginal slope be `(median(5k) - median(1k)) / 4,000` and the late slope be `(median(20k) - median(5k)) / 15,000`. For both full-build time and peak RSS above idle, the late slope must be no more than 1.25 times the positive early slope. A non-positive early slope makes the batch invalid and eligible for the single noise rerun. The 20,000-document run must complete without OOM, broker retention after record disposal, or an increasing retained-artifact count as completed records accumulate.

Hard gates decide acceptance. Targets show whether the kernel delivered the expected benefit and require an explanation in the release report if missed, but a missed target alone does not override a passing hard gate. Advisory observations are trend and diagnosis data only.

### CI, release gate, and stress-test execution policy

- Ordinary CI runs all deterministic invocation assertions, identity/mismatch/concurrency cases, correctness/equivalence cases, failed-record/build semantics, asset staging/publication tests, and broker disposal/retention checks. It also runs a 4-10 document built-`dist` benchmark smoke fixture that verifies both dialects, primary and projection-only demand, plugins, linked assets, outputs, and counters. Shared CI runners have no wall-time or RSS failure threshold.
- A pinned dedicated release host runs the complete 100-document statistical matrix, the 1,000-document mixed full/no-op/incremental benchmark, and peak-RSS gates for every release candidate. Results and environment metadata are retained as release artifacts.
- The same dedicated host runs the 1,000/5,000/20,000 stress series for every release candidate. A scheduled weekly run on the target branch may provide earlier trend detection, but only the protocol-valid release run gates a release.
- The implementation satisfies the Velite 1.0 content performance requirement only when every structural and correctness hard assertion passes, every valid numeric hard gate passes against the fixed adjacent baseline, the 20,000-document growth/retention checks pass, and the benchmark report contains enough metadata and raw samples to reproduce the decision.
- The designated release maintainer may approve exactly one complete rerun for a protocol-defined noisy or boundary result. The maintainer may not delete the first batch, change the fixture or threshold after seeing results, select favorable samples, or waive a hard structural/correctness assertion. Structural correctness, effect/diagnostic equivalence, record/broker disposal, no-cross-record sharing, and last-successful-generation publication semantics are never waivable as performance noise.
- Implementing the benchmark harness, counters, retention probes, CI workflow, or product optimization is follow-up implementation work after this map. This decision defines their acceptance contract and does not implement them.
