# Preserve VFile path and state across MDX processing phases

Status: ready-for-agent
Origin: #404 (deleted from GitHub)
Created: 2026-07-16T02:25:18Z
Labels: bug

## Problem

`ProcessMdxOptions.path` is accepted and populated by `s.mdx()`, but `processMdx` does not pass a path-aware VFile through `parse`, `run`, and `stringify`. Manual phase calls create or use separate empty file values, so plugins cannot reliably communicate through `file.data` or `file.messages`, and path-dependent diagnostics or compilation behavior do not receive the declared source path.

Evidence: `src/core/schema/mdx.ts` sets `path: file.path`; `src/core/content/mdx.ts` calls `processor.parse(source)`, `processor.run(mdast)`, and `processor.stringify(estree)` without a shared VFile.

## Expected behavior

Either preserve one path-aware branch VFile across all supported phases or remove the ineffective option and use an officially supported MDX processing path with equivalent file semantics.

## Design context

The supported phase split is being evaluated in [Choose the shared processing and cache architecture](05-choose-the-shared-processing-and-cache-architecture.md) and [Define plugin execution and isolation semantics](06-define-plugin-execution-and-isolation-semantics.md). Research evidence is recorded in [Establish the safe reuse boundaries of Unified and MDX processors](01-establish-the-safe-reuse-boundaries-of-unified-and-mdx-proce.md).

## Answer

> _This was generated by AI during triage._

**Verification:** Confirmed. `src/core/schema/mdx.ts` passes `file.path` as `ProcessMdxOptions.path`, but `src/core/content/mdx.ts` never constructs or passes a path-aware VFile to `parse`, `run`, or `stringify`. The option has no effect, and phase-local VFile state cannot be preserved.

**Disposition:** `subsumed-by-design`.

**Design coverage:** Decision 06 requires one logical, path-aware VFile through every Unified/MDX phase of a transforming branch. Decision 01 requires independent AST and VFile state per branch and warns that the current manual `parse -> run(mdast)` split is not a type-supported public `@mdx-js/mdx` contract.

**Implementation constraint:** The 1.0 MDX dialect adapter and processing branch replacing `src/core/content/mdx.ts` and its `src/core/schema/mdx.ts` caller must use one path-aware VFile for every supported parse, run, and stringify phase in that branch. `file.path`, `file.data`, and `file.messages` must remain available across phases without leaking to sibling branches. The implementation must use an officially supported `@mdx-js/mdx` processing path or explicitly own and test compatibility for any manual phase split.

**Acceptance test:** Install parse-, transform-, and compile-phase test plugins in an MDX branch. Assert that they observe the declared source path, that data written in an earlier phase is visible later, that messages accumulate on the same logical VFile, and that a sibling branch receives independent state. This test covers decisions 01 and 06.

## Reopened

The final design review found that this acceptance test is ambiguous: one shared pristine parse uses a parse-time VFile seed, while each transforming branch receives fresh mutable state. Ticket 22 must decide whether logical continuity means copying a defined parse-time seed or preserving object identity through parse, run, and stringify.

## Unblocked by Ticket 22

Ticket 22 defines logical continuity as supported observable state copied from an internal parse VFile seed into a fresh branch VFile, followed by object-identity continuity within that branch. This bug is ready for implementation when its regression tests verify canonical parse path/cwd, final history, independently copied supported data and parse messages, one VFile identity across the MDX branch's remark/rehype/recma/compile phases, and sibling isolation. The parse VFile object must not enter a transforming branch, and the current type-unsupported manual MDX phase split is not a stable seam.
